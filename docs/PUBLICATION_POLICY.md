# 发布规则：进行中的内容保持私有

开发工作可持续提交和备份；公开发布必须经过独立验收与批准。
新内容默认禁止公开，缺少发布字段也禁止公开。本规则覆盖 Git、PR、Release、网站、文章、
视频、截图、说明书与附件。`pub` 负责检查和导出，不自动联网、上传或批准任何内容。

## 两种状态

`status` 保持现有工程证据定义。`hardware-verified` 可能只有部分实机验证，不能代替项目完成。
发布单元必须达到 `stable` 且声明范围完整验收后才进入待审。

| `publication.state` | 含义 | 可公开 |
| --- | --- | --- |
| `draft` | 进行中、未完整验收，或尚未整理发布范围 | 否 |
| `ready` | 验收与隐私、许可审查通过，等待人类批准当前内容 | 否 |
| `approved` | 人类批准了具体目标、文件范围与摘要 | 检查通过后可导出；实际发布仍须在用户授权范围内 |
| `published` | 已按当次授权完成发布 | 当前内容与批准一致时才可再次导出 |

修改后的内容即使仍写着 `approved`，摘要不匹配也会被拦截。应主动退回 `ready`，重新审查。
只修改生命周期字段 `state` 或批准记录本身不会改变内容摘要；其他清单字段、目标、文件内容、
文件路径和可执行权限都属于批准范围。摘要使用 SHA-256。
清单按解析后的字段规范化计算摘要，改变 YAML 排版或注释不改变语义摘要。
导出时清单转换为规范 JSON（也是合法 YAML），不包含原文件注释；其他文件逐字节复制。

## 发布单元与清单

项目与 Demo 使用各自的 `project.yaml`；跨项目文档、工具、目录等使用
`publication/<id>.yaml`，从 [清单模板](../templates/publication.yaml) 创建。
一个清单只覆盖一个可独立验收的明确范围。父项目还在开发时，不能借另一个清单把未完成的
父项目包进去；后续若要公开独立的阶段成果，须明确它自己的范围、验收与依赖。
组合快照引用其他项目或 Demo 的文件时，必须同时纳入其清单；所属单元须达到 `stable`，
通过三个审查并处于 `ready`、`approved` 或 `published`，允许相同目标，而且这些文件必须
已经在所属单元的确切范围内。当前组合清单的批准摘要覆盖实际选取的所有文件。
缺少所属清单、所属单元仍在开发，或借组合清单扩大它的范围，都拒绝导出。

默认字段如下，禁止将完成意向写成审查结果：

```yaml
publication:
  state: draft
  acceptance: pending
  rights: unknown
  privacy: pending
  targets: []
  files: []
```

准备待审时，验收和真实审查通过后才能设置：

```yaml
status: stable
publication:
  state: ready
  acceptance: passed
  rights: cleared
  privacy: passed
  targets: [git]
  files:
    - publication/example.yaml
    - docs/example.md
    - LICENSE
```

`files` 必须列出**从仓库根开始的确切文件路径**，包括清单自身、正文、图片、代码、许可、
验证依据和依赖。不能填写目录、通配符、绝对路径或 `..`；新文件不会自动加入批准范围。
输入必须已受 Git 跟踪；本地尚未提交的内容也按当前实际字节审查，不依赖旧提交的摘要。
清单内容会随快照公开，因此不要把私人审核记录、身份、原始日志或本机路径写进清单。

`rights: cleared` 表示范围内每个文件的再分发许可已核验；`privacy: passed` 表示内容和图片
已人工检查并脱敏。这两个字段是审查结果记录，自动扫描不能代替实际审查。

## 命令

依赖 Python 3.9+ 和 Git。普通 YAML 清单需要 PyYAML：

```sh
python3 -m pip install PyYAML
```

本机访问公网安装依赖时，先使用 `setp`。检查器也支持 JSON 格式的 YAML 清单，使用标准库即可。

```sh
# 私有工作清单；输出可能包含未公开项目名称，不上传这份输出。
./scripts/pub status

# 查看整个开发树是否具有完整、有效的公开批准；当前开发树预期失败。
./scripts/pub --check

# 生成当前文件范围与摘要供人类审核，不写入批准。
./scripts/pub --json review publication/example.yaml --target git

# 人类批准并记录摘要后，检查这个具体单元。
./scripts/pub --check publication/example.yaml --target git

# 输出必须位于工作区之外，且尚不存在。
./scripts/pub export publication/example.yaml --target git --output ../example-public-snapshot
```

测试或其他检出目录可用 `--root PATH`。`--target platform` 使用同一门槛，但具有独立摘要：
Git 批准不能直接复用为平台发布授权。`--json` 提供可供其他发布工具调用的结果。
`status` 只列开发清单，输出中的 `configured` 只表示存在配置；`publication_checked: false`
明确表示尚未校验发布资格。发布工具必须使用 `--check` 成功结果，不能从清单状态自行推断放行。

审核者先检查 `review` 输出及文件，再明确批准当次目标和摘要。之后才可记录：

```yaml
  state: approved
  approval:
    sha256: "填入本次 review 给出的完整摘要"
    approved_by: "owner"
```

`approved_by` 采用不含个人资料的角色名。它记录人类批准，**不提供密码学身份认证**；
Agent 不得自行填写以绕过发布规则。实施机制的授权、本地 commit、项目验收和以前的发布
都不能自动生成这一批准。

导出只复制经过检查的确切文件，清单按上述规则规范化，不复制 `.git`、开发历史或旁边的新附件；不会覆盖已有目录。
校验与导出使用同一份读取的文件内容，导出后也应保持目录不可改动。
需要公开 Git 贡献时，将该快照应用到**另一个专供公开交付的 Git 仓库**，保持那个仓库的
已有历史与无关内容；绝不把开发分支 merge/cherry-pick 过去。实际 push、PR、Release 或平台
上传仍按用户当次授权执行。发布后可记录 `published`，命令本身不会替用户宣称已经发布。

## 开发历史与私有备份

本地仍保留完整项目与历史，公开首页及索引只列出当前批准有效的 `published` 单元。
开发清单使用 `pub status` 查看。新开发应保存在私有 Git 工作区与具有私有访问权限的远程。
现有公开远程保留用于读取；这次迁移不移动或删除原片、工程，也不清理或改写已有公开历史。
已经公开的旧内容不会因首页撤下、新字段或 `.gitignore` 而收回。

安装本地防误推送检查：

```sh
./scripts/pub install-hook
git config --local --get core.hooksPath
```

安装器拒绝覆盖既有不同钩子配置或钩子。安装成功后，`pre-push` 阻止从开发树向任何远程
直接推送，避免提交历史夹带草稿；即使某个单元批准了也只走快照出口。
每个新检出目录都需重新安装，仓库的 Git 本地配置不会通过克隆继承。

私有备份例外必须先由人类确认远程访问控制，并同时登记**远程名称和完整 URL**：

```sh
git config --local --add publication.privateRemote backup
git config --local publication.privateRemoteUrl.backup '<已确认私有的远程 URL>'
```

钩子只有在两者精确匹配时放行；改名或改 URL 后必须重新核对。工具不会把某个 URL 推断为
私有，也不会自动配置例外。本次不创建私有远程、不添加例外、不推送。

## 检查范围与边界

- 全树 `--check` 要求每个受跟踪文件都落在通过检查的发布单元范围内；没有清单、遗漏文件、
  草稿、无批准或批准过期均失败。单单元检查不授权范围之外的其他文件。
- 符号链接、越界路径、私有目录、凭据、原始日志和构建产物禁止进入快照；
  被忽略文件、命名为 `raw/` 等原始素材目录以及单文件超过 10 MiB 的内容会被拒绝。
  小型、已整理的媒体可显式列入范围，但须人工确认它不是原片且已脱敏、获准再分发。
  大体积媒体走独立私有生产流程，当前导出器不处理它，不能绕过门槛直接上传。
- 正文的本地 Markdown 链接/图片、HTML/SVG 的 `href`/`src` 与 CSS 资源引用必须有对应范围内文件。
  检查不访问远程链接，不替代任意代码导入、运行时资源、EDA、二进制或视频内容的人工依赖检查。
- 扫描常见凭据形式时只报告规则和文件路径，不回显疑似密钥。隐私审查仍须覆盖图片中的
  验证码、坐标、账号、地址和其他自动检查无法理解的内容。
- 公开上传工具必须使用 `pub --check` 和该次导出目录。`pub` 不拦截用户自行执行的第三方
  上传命令，不验证网站/平台访问控制，不保证生成产物的隐私或许可。
- 本地钩子可以被 `--no-verify` 或更改配置绕过，是防误操作机制。强制边界应由私有远程 ACL、
  公共仓库写权限隔离与专用发布账号提供；CI 在 push 后运行，无法撤回已经泄漏的内容。

## 验证与回退

```sh
python3 -m unittest discover -s tests -p 'test_publication.py' -v
```

测试用临时仓库和本地裸仓库验证批准、导出及实际推送拦截，不接触真实远程。
工程验证状态保持原值；这次机制实现不代表任何硬件验收完成。
如果需回退实现，应在私有开发分支回退对应提交；本地 `core.hooksPath` 是独立配置，
删脚本前先记录并恢复安装前配置，不要通过关闭钩子继续把开发历史推向公开远程。
